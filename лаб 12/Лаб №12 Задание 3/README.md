# Лабораторная работа №12 — вариант 17 (повышенный)
**JWT с обновлением сессии: короткий access token, безопасная ротация refresh token и выход**

Зависимостей нет — только Node.js ≥ 18. JWT (HS256) формируется и проверяется встроенным модулем `crypto`, чтобы работа запускалась без установки пакетов. В реальном проекте для JWT лучше использовать проверенную библиотеку (например, `jose`).


> **Как открыть без запуска чего-либо:** дважды щёлкните `index.html` в папке проекта. Приложение откроется в **демо-режиме**: серверная часть имитируется прямо в браузере (файл `public/mock-server.js`), поэтому ничего устанавливать и запускать не нужно. На странице при этом показывается жёлтая плашка. Это учебный **прототип**: в отчёте обязательно укажите, что скриншоты сделаны в демо-режиме с имитацией сервера, а настоящая серверная проверка реализована в `server.js` (запуск: `start.bat` или `npm start`, адрес http://localhost:3017).

Демо-режим лучше открывать в Chrome или Edge: он хранит состояние в sessionStorage, чтобы работало обновление страницы после входа.

## Запуск
```
npm start        # http://localhost:3017
npm test         # автотесты, пересоздаёт TEST_RESULTS.md
```
Переменные окружения: `JWT_SECRET` (если не задан — случайный секрет при каждом запуске, токены после перезапуска недействительны), `ACCESS_TTL_S` (по умолчанию 60), `REFRESH_TTL_S` (по умолчанию 7 суток), `SECURE=1` для HTTPS. Секрет в репозитории не хранится.

## Схема
```
POST /api/auth/login   → access JWT (в теле ответа, 60 с) + refresh token (cookie HttpOnly, Path=/api/auth)
GET  /api/profile      ← Authorization: Bearer <access>  → 200 | 401
GET  /api/admin/report ← Bearer; claim role=admin         → 200 | 403 | 401
POST /api/auth/refresh ← refresh cookie + X-Requested-With → новая пара токенов, старый refresh помечен «использован»
POST /api/auth/logout  ← refresh cookie                    → семейство токенов отозвано
```

## Как устроена безопасность
- **Access token** — JWT HS256 с claims `iss, aud, sub, role, sid, jti, iat, exp`. Сервер проверяет формат, алгоритм (только HS256, `alg=none` отвергается), подпись, срок, `iss`, `aud` и то, что сессия (`sid`) не отозвана. Клиент хранит токен только в переменной JS, не в localStorage.
- **Refresh token** — случайная строка (не JWT), cookie `HttpOnly; SameSite=Strict; Path=/api/auth`. На сервере хранится только SHA-256 от неё.
- **Ротация**: при каждом обновлении выдаётся новый refresh token, старый становится недействительным.
- **Обнаружение повторного использования**: если предъявлен уже использованный refresh token, вся цепочка (семейство) отзывается, и пользователь должен войти заново.
- **Выход** отзывает семейство: и refresh, и ещё не истёкший access token перестают приниматься сразу.
- Эндпоинты refresh/logout требуют заголовок `X-Requested-With` (дополнительно к SameSite) против CSRF.
- Права проверяются на сервере по роли из токена и по данным пользователя.

## Ограничения (учебный прототип)
- Хранилища семейств и refresh token — в памяти процесса; в реальной системе нужна БД/Redis.
- Нет ограничения числа попыток входа.
- HS256 с общим секретом подходит для одного сервера; для нескольких сервисов обычно берут асимметричную подпись.
- Для реального использования нужен HTTPS (`SECURE=1`).
